# 우리만의 여행 기록 앱 구현 계획

> 근거: `01-requirements.md`, `02-raw-travel-data.md`  
> 구현 전 설계 문서이며, 이 단계에서는 코드를 작성하지 않는다.

## 1. 제품 정의

이 앱의 중심 단위는 긴 카카오톡 공지가 아니라 **여행(Trip)** 이다. 동행 공간 안에서 여행마다 일정, 장소, 숙소, 교통, 음식, 레시피, 준비물, 예약, 메모, 사진을 연결하고, 끝난 여행은 삭제하지 않고 아카이브한다.

핵심 문제는 오래된 여행 탐색, 구조 없는 긴 텍스트, 준비물 중복과 역할 분배, 공동 메모의 편집 제약, 사진과 장소 기록의 분리다. 따라서 모든 내용을 단일 `content` 컬럼에 저장하지 않고, 구조화 가능한 데이터는 엔티티로 분리하되 행사 부스 목록·숙소 안내 같은 자유 형식 기록은 메모로 손실 없이 보존한다.

## 2. 요구사항 분류

### MVP

- 로그인, 동행 공간 생성/초대, 커플·친구 관계 유형
- 여행 생성/목록/상세/아카이브
- 기간, 지역, 숙소, 체크인/체크아웃, 예약, 교통
- 날짜별 일정과 식사 계획
- 장소 후보/확정/방문 관리 및 네이버·카카오 지도 외부 열기
- 공용/개인 준비물, 담당자, 준비·구매 위치, 체크 상태
- 작성자와 시각이 남는 공동 메모
- 사진 업로드와 여행/날짜/장소/일정 연결
- 여행 제목·장소·음식·준비물·메모 기본 검색

### 이후 단계

- 앱 내 지도 SDK, 경로와 핀 지도
- 레시피 재료의 자동 장보기 생성, 푸시 알림, 완전 오프라인 동기화
- 카메라 자동 업로드, 사진 꾸미기, OCR/AI 공지 마이그레이션
- 세분화된 권한과 변경 이력

### 암묵적 요구사항

- 여행 중 빠르게 체크, 메모, 사진을 추가할 수 있어야 한다.
- 동일 장소가 여러 여행에서 재등장해도 일관되게 검색되어야 한다.
- 초기에는 둘이 쓰더라도 3명 이상 친구 그룹으로 확장 가능해야 한다.

## 3. 실제 데이터 분석과 결정

| 실제 데이터 패턴 | 설계 결정 |
| --- | --- |
| 우사기쇼쿠도·오늘초밥이 여러 여행에서 반복 | 전역 `Place`와 여행별 `TripPlace`를 분리 |
| 후보 식당, 예약 식당, 일정의 점심 | 장소 상태와 일정 연결을 둠 |
| JS호텔/초량머뭄, 체크인·체크아웃·야놀자 링크 | `Accommodation`과 `Reservation` 분리 |
| KTX와 버스가 사람별로 존재 | 구간·시간·수단·예약자/탑승자를 가진 `Transportation` |
| 밀푀유나베 재료·육수·소스·담당 | `Recipe → RecipeIngredient → ChecklistItem` 연결 |
| 집에서 가져오기와 현지 구매 | 준비물의 `acquisition_type`으로 구분 |
| 세인/찬희별 물품, 아침에 챙길 것 | 담당자·공용 여부·준비 시점 필드 |
| 드론쇼, 행사 부스 목록, 숙소 수령 안내 | 일정/장소에 연결 가능한 자유 `Memo` 유지 |
| 네이버·카카오·구글 지도 및 야놀자 URL | 제공자와 URL을 가진 `ExternalLink`로 저장 |

원문을 전부 자동 변환하기보다, 원문 블록을 메모로 보존하고 사용자가 필요한 항목을 구조화한다. 이 방식은 실제 데이터의 예외를 잃지 않는다.

## 4. 도메인 모델

### 공간과 사용자

- `User`: 인증 계정, 표시 이름, 프로필 사진, 시간대.
- `Space`: 함께 여행을 관리하는 단위. `relationship_type`은 `couple`, `friends`, `other`.
- `Membership`: 사용자와 공간의 연결. 역할은 `owner`, `editor`, `viewer`.
- `RelationshipProfile`: 공간별 부가 관계 정보. 커플일 때만 `started_on` 저장.

### 여행과 계획

- `Trip`: 제목, 지역 문자열, 시작/종료일, 상태(`planning`, `ongoing`, `archived`), 대표 사진, 설명.
- `TripDay`: 여행 안의 날짜. 날짜별 타임라인 기준.
- `ScheduleItem`: 시간, 제목, 유형(식사/관광/행사/교통/자유), 정렬 순서, 메모. `TripDay`, `TripPlace`에 연결.
- `Place`: 재사용 가능한 정규 이름, 카테고리, 주소, 좌표, 지도 링크.
- `TripPlace`: 여행 내 사용 문맥. 상태(`candidate`, `planned`, `reserved`, `visited`), 지역 구역 라벨, 여행별 메모.
- `Accommodation`: 숙소명, 장소, 체크인/아웃, 출입·수령 안내.
- `Reservation`: 숙소/식당/교통/기타 예약의 일시, 상태, 예약자, 링크, 확인번호, 메모.
- `Transportation`: 출발/도착, 시각, 수단, 편명, 예약자, 탑승자, 예약 연결.
- `MealPlan`: 날짜·끼니·메뉴. 일정과 장소에 선택적으로 연결.
- `Recipe`: 해먹을 음식 제목, 인분, 조리 순서, 출처, 메모.
- `RecipeIngredient`: 재료, 수량, 단위, 섹션(기본/육수/소스/추가), 선택 여부.

### 준비와 기록

- `Checklist`: 공용 준비물, 장보기, 아침에 챙길 것 같은 목록 묶음.
- `ChecklistItem`: 이름, 수량, 완료, 공용 여부, 담당자, 준비 시점, `acquisition_type`(`bring_from_home`, `buy_local`, `buy_before_trip`, `other`), 원본 재료 연결.
- `Memo`: 본문, 작성자/수정자, 생성/수정/삭제 시각. 날짜·장소·일정·숙소에 선택적으로 연결.
- `Photo`: 스토리지 키, 촬영 시각, 업로더, 썸네일/원본 메타데이터. 날짜·장소·일정·숙소 연결 지원.
- `ExternalLink`: URL, 제공자(`naver_map`, `kakao_map`, `google_map`, `yanolja`, `other`), 라벨. 장소·예약·숙소·메모에 연결.

## 5. 관계와 무결성

```text
User ──< Membership >── Space ──< Trip ──< TripDay ──< ScheduleItem
                                │             │             └── TripPlace >── Place
                                │             ├──< MealPlan ──> Recipe ──< RecipeIngredient
                                │             ├──< Checklist ──< ChecklistItem >── Membership
                                │             ├──< Reservation / Transportation / Accommodation
                                │             ├──< Memo
                                │             └──< Photo
                                └── RelationshipProfile (couple일 때만 시작일)
```

- 하위 데이터는 언제나 부모 `Trip`과 동일한 `Space`에 속해야 한다.
- 레시피에서 생성한 준비물은 `source_recipe_ingredient_id`를 저장하되, 준비물 수정은 레시피 원문을 바꾸지 않는다.
- 전역 장소의 이름/주소와 여행별 상태/메모를 분리한다.
- 삭제는 소프트 삭제를 기본으로 하고 사진 원본은 참조가 모두 사라진 뒤 비동기 정리한다.

## 6. 권한과 공동 편집

| 동작 | owner | editor | viewer |
| --- | --- | --- | --- |
| 여행·일정·장소·예약 수정 | 가능 | 가능 | 불가 |
| 준비물 담당자/체크 변경 | 가능 | 가능 | 불가 |
| 본인 메모 수정/삭제 | 가능 | 가능 | 불가 |
| 타인 메모 삭제 | 가능 | 가능 | 불가 |
| 멤버 초대/권한 변경 | 가능 | 불가 | 불가 |

둘만의 공동 공간 요구에 맞춰 `editor`도 타인 메모를 삭제할 수 있게 한다. 삭제자·삭제 시각은 감사 로그에 남기며, 그룹 사용 시 공간 설정으로 제한할 수 있게 확장한다.

## 7. 커플/친구 모델

여행 기능은 모두 `Space`에 공통으로 두고, 커플 전용 정보만 `RelationshipProfile`에 둔다. 공간 시간대(기본 `Asia/Seoul`)의 날짜 기준으로 계산하며, 시작일을 1일째로 한다: `days_between(started_on, target_date) + 1`.

커플 공간의 홈에는 현재 일수를, 여행 상세에는 `Trip.start_date` 기준 “사귄 지 N일째에 떠난 여행”을 표시한다. 친구/기타 공간에는 관련 필드와 UI를 노출하지 않는다.

## 8. 모바일 UX

하단 탭은 `홈 · 여행 · 검색 · 설정`으로 구성한다.

- **로그인/온보딩**: 로그인 → 공간 생성/초대 참여 → 관계 유형 선택. 커플이면 시작일 입력.
- **홈**: 다음 여행, 공용 미완료 준비물, 최근 메모/사진. 커플 공간에는 현재 N일째.
- **여행 목록**: 예정/진행/아카이브 필터, 기간·지역·대표 사진, 검색.
- **여행 생성**: 제목, 기간, 지역, 공간, 숙소.
- **여행 상세**: `일정 · 장소 · 음식 · 준비 · 메모 · 사진 · 정보` 탭. 숙소·예약·교통은 정보와 관련 일정에 함께 표시.
- **일정**: 날짜별 타임라인에서 식사·행사·이동·장소를 함께 표시.
- **장소**: 후보/예약/방문 상태, 네이버·카카오 지도 열기.
- **음식/레시피**: 먹고 싶은 곳, 예약 식당, 해먹을 음식, 레시피. 재료를 준비물에 추가.
- **준비**: 담당자/공용/집에서 가져오기/현지 구매 필터와 체크 토글, 중복 경고.
- **메모/사진**: 대상별 필터, 카메라/앨범 빠른 추가.

## 9. 지도·사진·검색

### 지도

MVP는 지도 SDK를 내장하지 않고 네이버 지도와 카카오맵 딥링크/웹 링크를 외부로 연다. 현재 공지의 링크 사용 방식을 가장 빨리 대체하며 SDK 키·약관·좌표 품질 문제를 피한다. 이후 `Place.latitude/longitude`와 제공자별 외부 ID를 활용해 앱 내 핀 지도와 경로 보기로 확장한다.

### 사진

촬영/앨범 선택 후 EXIF 촬영 시각을 읽고 여행 기간 안이면 날짜를 자동 제안한다. 업로드 전 긴 변 2,560px 리사이즈, GPS는 동의 없으면 제거한다. 원본(선택), 표시용, 썸네일을 분리하고 DB에는 경로와 메타데이터만 저장한다. 서명 URL로 직접 업로드한 뒤 서버가 권한과 파일을 검증해 `Photo`를 확정한다.

### 검색

MVP 범위는 여행 제목·지역, 장소, 일정, 음식/레시피, 준비물, 메모다. 결과는 유형과 여행명, 날짜/장소 문맥을 표시해 상세로 이동한다. 초기에는 PostgreSQL 전문 검색과 `pg_trgm`을 사용하고, 별도 검색 서버는 두지 않는다.

## 10. 기술 스택과 아키텍처

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 앱 | React Native + Expo + TypeScript | iOS/Android 단일 코드와 카메라·이미지·알림 생태계 |
| 화면/상태 | Expo Router, TanStack Query, Zustand | 서버 상태와 임시 폼 상태를 분리 |
| 백엔드 | Supabase | 초기 소규모에 Auth, PostgreSQL, RLS, Storage, Functions 제공 |
| 이미지 | Supabase Storage + 이미지 변환 CDN | 권한 있는 업로드와 썸네일을 간단히 운영 |
| 검색 | PostgreSQL FTS + pg_trgm | 낮은 운영비로 한국어 부분 검색 보완 |
| 알림 | Expo Push Notifications (후속) | 일정·체크 알림을 낮은 비용으로 확장 |

클라이언트는 화면 → feature repository/service → Supabase 순서로 접근한다. 단순 CRUD는 RLS로 보호하고, 초대·검색·사진 확정처럼 민감하거나 트랜잭션이 필요한 작업은 Edge Function으로 처리한다. 클라이언트가 넘긴 `space_id`는 권한 근거로 신뢰하지 않는다.

## 11. API와 프로젝트 구조

서버 함수/트랜잭션이 필요한 핵심 동작은 다음과 같다.

- `POST /spaces`: 공간과 생성자 membership 생성
- `POST /spaces/{spaceId}/invites`, `POST /invites/{token}/accept`: 초대와 가입
- `POST /trips`: 여행과 기간의 `TripDay`를 한 트랜잭션으로 생성
- `POST /trips/{tripId}/recipe-ingredients/{id}/checklist-items`: 재료에서 준비물 생성
- `POST /trips/{tripId}/photos/upload-url`, `/complete`: 사진 업로드 권한 발급 및 확정
- `GET /spaces/{spaceId}/search?q=`: 권한 범위 통합 검색

```text
app/                    # Expo Router 화면
src/features/           # trips, places, recipes, checklist, memo, photos, spaces
src/components/         # 공통 UI
src/lib/                # Supabase, 시간대, 링크, 권한 유틸리티
src/types/              # DB·도메인 타입
supabase/migrations/    # 스키마, 인덱스, RLS
supabase/functions/     # 초대, 검색, 사진 서버 함수
docs/                   # 요구사항, 원본 데이터, 설계 문서
```

모든 엔티티에는 UUID, `created_at`, `updated_at`, `created_by`를 둔다. 수정 요청은 `updated_at` 또는 `version`을 함께 보내 오래된 편집을 감지한다.

## 12. MVP 개발 순서

1. Expo/TypeScript/Supabase 프로젝트, 환경 변수, CI, 인증 골격.
2. `Space`·`Membership`·초대와 RLS, 커플/친구 설정.
3. `Trip`·`TripDay`의 생성/목록/상세/아카이브.
4. 숙소, 예약, 장소, 지도 링크, 일정/식사/교통.
5. 체크리스트, 담당자, 집/현지 구매 구분과 중복 경고.
6. 공동 메모, 사진 업로드/앨범.
7. 통합 검색, 빈 상태, 오류 처리, 접근성/성능.
8. 실제 원문 6건을 시드로 입력해 모델 누락을 검증.

가장 먼저 구현할 작업은 **공간/멤버십/여행/날짜/장소의 스키마와 RLS를 포함한 최소 수직 슬라이스**다. 이것이 정해져야 나머지 기능이 같은 여행 문맥과 권한 경계에 안전하게 연결된다. 이어 `8월 21일~23일 서울 구로구` 원문을 시드로 옮겨 레시피→재료→준비물, 예약, 숙소, 일정 모델을 검증한다.

## 13. 테스트와 배포

- 단위: 연애 일수, 여행 날짜 생성, 준비물 중복 탐지, URL 제공자 판별, 권한 판정.
- DB/RLS: 다른 공간 데이터 차단, viewer 수정 차단, editor 공동 메모 삭제.
- 통합/E2E: 여행 생성 → 장소/예약/일정 → 레시피 재료 → 담당/체크 → 사진/메모 → 검색; iOS/Android 카메라 권한 거부와 외부 지도 열기 포함.
- 마이그레이션 회귀: 서울 구로·평촌·안양·부산·진주 원문으로 KTX/버스, 행사, 숙소 안내, 개인 준비물, 지도 링크가 손실되지 않는지 확인.
- 운영: 개발/스테이징/운영 Supabase를 분리하고 Expo EAS로 TestFlight/Android 내부 테스트에 배포한다. 오류 추적, DB 백업, 스토리지 사용량을 설정한 뒤 두 사용자가 실제 다음 여행을 앱만으로 계획·기록하는 파일럿을 진행한다.

## 14. 향후 확장

내부 지도와 경로, 반복 준비물 템플릿·여행 복제, 일정/담당자 알림, 사진 타임라인·회고 카드, 원문 붙여넣기 구조화 보조, 더 큰 그룹을 위한 권한·변경 이력을 차례로 추가한다.
