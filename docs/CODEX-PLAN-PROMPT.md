# Codex 계획 수립 프롬프트

이 저장소는 두 명 이상의 동행자가 여행을 계획하고 준비하고 기록하기 위한 모바일 앱 프로젝트를 만들기 위한 것이다.

현재 계획은 `development/`에 정리되어 있다. 개발을 시작하기 전 해당 문서와 현재 UI 코드를 함께 읽고, 진행할 단계의 결정사항을 사용자에게 확인하라.

## 반드시 읽을 파일

1. `01-requirements.md`
   - 제품을 만들게 된 배경과 사용자가 직접 설명한 요구사항
2. `02-raw-travel-data.md`
   - 현재 카카오톡 공지에서 실제로 사용하고 있는 원본 여행 데이터
3. `development/README.md`와 연결된 문서 전체
   - 현재 UI를 기준으로 확정된 개발 환경, API, 데이터 모델, 단계별 계획, 품질 기준
4. `../mobile/src/WarmAppShell.tsx`, `../mobile/src/WarmTripDetail.tsx`
   - 실제 사용자 검토를 거친 최신 UI와 동작

문서와 UI의 내용을 모두 읽고 분석하라. 과거 계획과 최신 UI가 다르면 최신 UI와 `development/` 문서를 우선하되 요구사항 원문을 누락하지 않는다.

## 중요한 원칙

### 1. 요구사항을 임의로 축소하지 말 것

`01-requirements.md`의 요구사항은 사용자가 실제로 원하는 기능이다.

`02-raw-travel-data.md`의 데이터는 실제 사용 사례다.

두 파일을 읽고 실제 데이터에서 반복되는 패턴을 찾아야 한다.

### 2. 원본 데이터의 모든 형태를 고려할 것

실제 데이터에는 다음과 같은 형태가 섞여 있다.

- 날짜
- 지역
- 숙소
- 네이버 지도 URL
- 카카오맵 URL
- 구글맵 URL
- 야놀자 URL
- 예약 정보
- 체크인/체크아웃
- 기차
- 버스
- 일정
- 음식
- 식당
- 식당 후보
- 예약한 식당
- 레시피
- 재료
- 재료 수량
- 소스
- 육수
- 집에서 준비할 것
- 현지에서 구매할 것
- 개인 준비물
- 공용 준비물
- 담당자
- 체크 여부
- 메모
- 행사
- 전시
- 장소별 구분
- 지역별 구분
- 사진
- 여행 기록

이것들을 단순히 하나의 `content` 텍스트 컬럼으로 저장하는 방향을 기본 설계로 선택하지 말라.

### 3. 여행 중심 도메인으로 생각할 것

앱의 가장 중요한 단위는 긴 게시글이 아니라 `여행(Trip)`이다.

여행을 중심으로 다음 데이터가 연결될 수 있어야 한다.

- 일정
- 장소
- 숙소
- 교통
- 음식
- 레시피
- 준비물
- 역할
- 예약
- 메모
- 사진

### 4. 장소는 재사용 가능한 데이터가 될 수 있어야 한다

같은 장소가 여러 여행에서 등장할 수 있다.

예를 들어 실제 데이터에서 `우사기쇼쿠도`, `오늘초밥`처럼 여러 여행에서 다시 등장하는 장소가 있다.

따라서 여행에 종속된 단순 문자열과 전역적으로 재사용 가능한 장소 정보를 구분할 필요가 있는지 검토하라.

### 5. 준비물과 음식 재료의 연결을 고려할 것

실제 사용자는 해먹을 음식의 재료를 준비하고 있으며, 일부는 집에서 가져오고 일부는 현지에서 구매한다.

다음 흐름을 지원할 수 있는 데이터 모델을 검토하라.

`레시피 → 재료 → 준비 목록 → 담당자 → 체크`

또한:

`집에서 가져오기 / 현지 구매`

를 구분할 수 있어야 한다.

### 6. 관계 유형

이 앱은 연인만을 위한 앱이 아니다.

친구와도 사용할 수 있어야 한다.

따라서 특정 사용자 관계를 `커플`로 하드코딩하지 말고 동행 공간 또는 그룹의 관계 유형을 확장 가능한 형태로 설계할 것.

예:

- couple
- friends
- 기타 향후 확장 가능한 관계 유형

### 7. 커플 모드

커플 관계에서는 연애 시작일을 저장하고 여행 날짜와 연결할 수 있으면 좋다.

예:

- 사귄 지 100일째에 방문한 여행
- 사귄 지 250일째에 방문한 여행

그리고 평소 앱에서도 현재 사귄 지 며칠째인지 표시할 수 있으면 좋다.

이 기능은 커플 관계에서만 활성화되고, 친구 관계에서는 연애 일수와 같은 표현이 노출되지 않아야 한다.

단, 정확한 일수 계산 방식, 시작일 포함 여부, 시간대, 날짜 변경 기준 등은 계획 단계에서 정의해야 한다.

## Codex가 수행할 작업

다음 순서로 분석하고 계획을 작성하라.

### Step 1. 요구사항 분석

`01-requirements.md`를 기준으로:

- 명시적 요구사항
- 암묵적 요구사항
- 해결하려는 문제
- MVP에 반드시 필요한 기능
- 이후 단계로 미뤄도 되는 기능

을 구분하라.

### Step 2. 실제 데이터 분석

`02-raw-travel-data.md`를 기준으로:

- 반복되는 데이터 패턴
- 서로 연결되는 데이터
- 하나의 엔티티로 분리할 필요가 있는 데이터
- 단순 메모로 남겨야 하는 데이터
- 데이터 모델링 시 주의해야 하는 예외

를 정리하라.

### Step 3. 도메인 모델 후보

다음 엔티티를 출발점으로 검토하되, 반드시 실제 데이터에 맞춰 수정하라.

- User
- Space / Group
- Membership
- Trip
- TripDay
- Schedule
- Place
- TripPlace
- Accommodation
- Reservation
- Transportation
- Meal
- Recipe
- Ingredient
- Checklist
- Memo
- Photo

필요하면 엔티티를 추가하거나 합쳐라.

각 엔티티가 왜 필요한지 설명하라.

### Step 4. 관계 모델

특히 다음 관계를 명확히 설계하라.

- 사용자 ↔ 공간
- 공간 ↔ 여행
- 여행 ↔ 날짜
- 여행 ↔ 장소
- 여행 ↔ 일정
- 여행 ↔ 음식
- 음식 ↔ 레시피
- 레시피 ↔ 재료
- 재료 ↔ 준비물
- 준비물 ↔ 담당자
- 여행 ↔ 예약
- 여행 ↔ 교통
- 여행 ↔ 메모
- 여행 ↔ 사진
- 사진 ↔ 날짜
- 사진 ↔ 장소
- 사진 ↔ 일정

### Step 5. 모바일 앱 UX

iOS / Android를 모두 고려하여 화면 구조를 계획하라.

최소한 다음 화면을 검토하라.

- 로그인/가입
- 공간 생성/초대
- 여행 목록
- 여행 생성
- 여행 상세
- 일정
- 지도
- 장소
- 음식/레시피
- 준비물
- 메모
- 사진
- 여행 기록/아카이브
- 설정

커플 모드에서 현재 연애 일수를 어디에 표시할지도 계획에 포함하라.

### Step 6. 지도 연동

네이버 지도와 카카오 지도 지원 요구사항을 반영하라.

다만 지도 SDK를 앱 내부에 직접 넣는 것과 외부 지도 앱/웹 링크를 여는 것의 차이를 설명하고, MVP와 이후 단계에서 어떤 방식을 사용할지 제안하라.

### Step 7. 사진 저장

사진을 앱에 업로드하고 여행/날짜/장소/일정과 연결하는 구조를 계획하라.

앱 내 카메라 버튼에서 촬영 후 빠르게 업로드하는 UX도 고려하라.

스토리지, 이미지 메타데이터, 썸네일, 원본 이미지 처리 방식도 계획 단계에서 검토하라.

### Step 8. 검색

전체 여행 기록에서 장소, 음식, 준비물, 메모 등의 데이터를 검색할 수 있는 방법을 계획하라.

### Step 9. 권한/편집

둘만 사용하는 공간의 특성을 고려하되 향후 친구 그룹으로 확장할 수 있도록 권한 모델을 검토하라.

특히:

- 내가 작성한 메모 수정
- 내가 작성한 메모 삭제
- 다른 사람이 작성한 메모 삭제
- 준비물 담당자 변경
- 체크 상태 변경
- 여행 정보 수정

등을 누가 할 수 있는지 정의하라.

### Step 10. 기술 스택

iOS/Android를 함께 지원하는 기술 스택을 비교하고 하나를 추천하라.

백엔드, DB, 인증, 이미지 저장소, 지도 연동, 검색, 푸시 알림 등이 필요한지 판단하라.

특히 이 앱의 사용자가 매우 적은 초기 단계라는 점을 고려하여 과도한 인프라를 만들지 말라.

### Step 11. MVP 정의

MVP는 실제 카카오톡 공지를 대체할 수 있는 수준이어야 한다.

최소한 다음을 기준으로 판단하라.

- 여행 생성/목록
- 여행 상세
- 일정
- 숙소
- 장소
- 네이버/카카오 지도 링크
- 준비물
- 담당자
- 체크
- 메모
- 사진
- 기본 검색

그 외 기능은 MVP 이후로 분류할 수 있다.

### Step 12. 구현 계획

최종적으로 다음 내용을 포함한 구현 계획을 작성하라.

1. 프로젝트 구조
2. 기술 스택
3. 아키텍처
4. 데이터 모델
5. API 설계
6. 모바일 화면 구조
7. 인증/권한
8. 파일/사진 저장
9. 검색
10. 지도 연동
11. 커플/친구 관계 모델
12. MVP 개발 순서
13. 단계별 구현 작업
14. 테스트 전략
15. 배포 전략
16. 향후 확장 계획

## 결과물 형식

계획만 작성하라.

아직 코드를 작성하지 말라.

계획에는 각 결정에 대한 이유를 함께 적어라.

특히 실제 데이터에서 어떤 요구사항을 발견했는지 근거를 명시하라.

추상적인 "여행 앱을 만든다" 수준의 계획이 아니라, `02-raw-travel-data.md`의 실제 데이터가 어떻게 도메인 모델과 화면으로 변환되는지 보여주는 계획을 작성하라.

계획을 완료한 뒤 구현 단계에서 가장 먼저 해야 할 작업부터 우선순위를 부여하라.
