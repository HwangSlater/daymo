초대와 멤버(2026-09-16):

- **초대 링크**는 `https://api.daymo.xyz/auth/invite?token=...`. 페이지가 공간을 드러내지 않고 `daymo://invite?token=...`으로 앱을
  연다. 앱은 링크로 열리면 token을 받아 두었다가 로그인 뒤 "참여할까요?"를 묻는다. 앱이 안 열리면 우리 → 멤버 관리 →
  "초대 링크로 참여"에 붙여 넣는다(`mobile/src/inviteLink.ts`가 글에 섞인 링크에서도 token을 꺼낸다)
- **초대 링크 보내기**(owner·editor)는 링크를 만들자마자 복사하고 공유 창을 연다. 원문은 그때만 받을 수 있다
- **관리자**는 고른 멤버의 권한(편집 가능·보기만)을 바꾸고, 관리자를 넘기고, 내보낸다. 누구나 나갈 수 있고,
  다른 멤버가 있는 관리자는 서버가 먼저 넘기라고 답한다
- **고친 것:** 공간 목록을 다시 받을 때 처음 읽은 설정의 공간과 비교해, 초대로 들어간 공간으로 옮겨 가자마자 첫 공간으로 되돌아가던 문제
- 확인: 로컬 웹 빌드로 다른 계정이 만든 링크를 글과 함께 붙여 넣어 참여 → editor로 들어가고 그 공간으로 옮겨 감,
  들어간 공간에서 초대 링크 만들기, 초대 페이지 200·앱 링크 포함

신고와 차단(2026-09-16):

- **신고**는 메모·일기·사진의 창과 멤버 관리에서 누른다. 사유를 고르고 설명을 1000자까지 적는다. 같은 대상을 다시
  신고하면 처음 접수 번호를 그대로 준다. 한 사람이 한 시간에 10건까지다
- **차단**은 멤버 관리에서 사람을 골라 누르고 같은 자리에서 푼다. 앱은 남의 사용자 id를 모르므로 membership id로 가리킨다
- **차단이 실제로 막는 것은 초대 수락 하나다.** 이미 같은 공간에 있는 사람의 기록을 숨기거나 지우지 않는다. 공동 기록이
  어긋나기 때문이고, 대신 나가기나 내보내기를 안내한다
- 새 신고마다 `support@daymo.xyz`로 접수 번호·대상 종류·사유·검토 기한만 보낸다. 설명과 대상 내용은 넣지 않는다
- 자세한 계약은 `03` 문서 2장

보기 전용 멤버(viewer, 2026-09-16):

- 관리자가 멤버 권한을 `보기만`으로 내리면 생긴다. 초대로 들어오는 사람은 늘 `편집 가능`이다
- 서버는 조회만 허용하고 쓰기·휴지통·초대를 전부 `FORBIDDEN(403)`으로 막는다
- **앱 화면에서는 아직 고칠 수 있다.** 저장만 거부되고 "보기만 권한" 안내가 뜬다. 화면에서 미리 막는 것은 남았다

3번 중 사진을 하며 남긴 것:

- **서버:** `POST /trips/{id}/photos`(줄과 한도) → `PUT /photos/{id}/content`(파일 그대로) 두 번에 올린다. 서버가 SHA-256을 맞추고
  EXIF를 뺀 표시본(2048px)·썸네일(480px)을 만든다. 파일은 `/srv/daymo/uploads/trips/{여행}/{사진}/`, 전달은 API의 `FileResponse`.
  지운 사진은 7일, 멈춘 올리기는 하루 뒤 정리 작업이 파일째 지운다. VPS 사진 폴더 소유자를 컨테이너 uid 10001로 맞췄다
- **앱:** 코덱은 `mobile/src/photoSync.ts`(설명·날짜만 오간다), 파일은 `photoTransfer.ts`. 폰은 `FileSystem.uploadAsync`로 파일을 JS에
  올리지 않고 보낸다. 다른 기기의 사진은 표시본을 문서 폴더에 받아 둔다(폰만). 사진 자체를 바꾸면 새 사진으로 올린다
- **영수증:** 지출의 영수증 파일을 사진(`isReceipt`)으로 올린 뒤 지출에 `receiptPhotoId`를 붙인다. 다른 기기가 붙인 영수증은 받아 둔다
- **로그인 풀림 고침:** 토큰 갱신 뒤 다시 보낸 요청이 422 등으로 실패해도 로그인을 풀던 문제를 고쳤다(`withAccessToken`)
- **그 뒤에 붙인 것:** 휴지통 조회·복원(아래 "휴지통"), 원본의 위치정보 제거, `PHOTO_ACCEL_PREFIX`를 넣으면 Nginx가 보내는 X-Accel-Redirect
- **아직 없는 것:** 중복 사진 안내, 사용량 화면, 삭제 ledger, 올린 사람이 아닌 editor가 남의 사진을 고칠 때의
  안내 문구(지금은 보기만 권한 안내가 뜬다)
- 확인: 로컬 웹 빌드로 옛 사진(파일 있음)·예시 사진(파일 없음)·영수증 지출 옮기기 → 파일 있는 사진과 영수증만 올라감, 썸네일·영수증
  받기 200, 다른 기기의 사진이 다시 열면 목록에 보임, 남의 사진 수정 403

3번 중 메모·일기를 하며 남긴 것:

- **메모와 일기가 서버에 간다.** 코덱은 `mobile/src/memorySync.ts`. 메모의 작성자 줄(`하늘 · 오늘 10:42 · 수정됨`)은
  서버의 작성자와 시각으로 만들고, 앱은 본문만 보낸다. 예전에는 새 메모의 작성자가 `하늘`로 박혀 있었다
- **일기의 날짜는 `writtenOn`(그 일기가 다루는 날).** 여행 중에 쓰면 오늘이고, 여행 밖에서 쓰면 비워 두고 쓴 날로 보인다.
  제목을 비우면 비운 채 저장하고 화면에서만 `이번 여행 이야기`로 보인다
- **메모를 지우면 서버에 행이 남는다.** 7일 안에는 메모 시트의 휴지통에서 되돌린다(사진도 함께)
- 확인: 로컬 웹 빌드로 옛 메모·일기 옮기기, 다른 기기의 메모 추가·고침·일기 추가가 다시 열면 작성자·수정됨·날짜와 함께 보임

사람 묶기를 하며 남긴 것:

- **화면은 계속 이름을 들고, 이름이 곧 한 사람이 되게 했다.** 이름을 id로 통째로 바꾸면 상세 화면 전체를 고쳐야 해서,
  대신 사람 표(`rosterOf`)의 이름을 겹치지 않게 만들고(`하늘 2`, `공용`·`미정`·`구매`와 같은 이름도 번호) 여행마다
  `personNames`(`membership id → 이름`)를 저장한다. 코드는 `mobile/src/people.ts`
- **멤버가 이름을 바꾸면 여행을 열 때 기록 곳곳의 옛 이름을 새 이름으로 바꾼다**(참가자·준비물·재료·교통편·지출·몫·주고받은 기록).
  두 사람이 이름을 맞바꿔도 한꺼번에 바꿔 섞이지 않는다. 표를 아직 못 받은 채로 열면 다음에 연다
- **나간 멤버도 표에 넣는다**(`GET /spaces/{id}/members?includeLeft=true`). 나간 사람이 낸 지출·맡은 준비물이 이름 그대로 보이고
  서버에도 올라간다. "우리" 탭 멤버 목록에는 나오지 않는다. 이미 참가자인 나간 멤버는 참가자 교체 때 빠지지 않는다
- **이름 바꾸기 API는 아직 없다.** 확인은 DB에서 별명을 바꿔 했다
- 확인: 로컬 웹 빌드로 여울 별명을 바꾸고 새봄을 내보낸 뒤, 옛 이름으로 적힌 오프라인 지출이 새 이름으로 바뀌어 여울의 것으로
  올라감, 새봄이 맡은 준비물이 그대로 보이고 서버 담당도 유지

3번 중 준비·요리를 하며 남긴 것:

- **준비물과 요리가 서버에 간다.** 코덱은 `mobile/src/cookingSync.ts`. 앱은 체크를 목록 밖(`packingDone`,
  `cookingReadyIngredientIds`)에 두므로 맞출 때만 줄에 붙여 보고, 서버 모습이 오면 둘로 다시 나눈다
- **여행마다 준비물 목록 하나를 서버가 처음 쓸 때 만든다.** 체크는 `completed` 참/거짓으로 오가고 누가 했는지는 서버에만 남는다
- **재료는 요리와 함께 배열로 오간다.** 서버는 id가 같은 재료를 고치고 빠진 재료만 지운다. 재료 id도 UUID여야 올라가서,
  준비물·요리·재료의 새 id를 모두 `Crypto.randomUUID()`로 바꾸고 옛 id는 여행을 열 때 한 번 옮긴다
- **담당:** 준비물의 `공용`은 `isShared`, `미정`은 비움. 재료의 `구매`는 `procurement=buy`, 사람은 `bring`
- **재료를 준비물로 가져오면 연결(`sourceIngredientId`)이 남는다.** 재료가 서버에 올라간 뒤에 보내고, 준비물 줄에는
  `버섯전골 재료`처럼 옅게 보인다. 이름이 서로 달라졌으면 `버섯전골 · 알배추`로 재료 이름까지 보인다.
  요리나 재료를 지우면 준비물은 남고 표시와 연결만 사라진다
- **준비물 중복은 기기에서 안내한다.** 견주는 규칙은 `mobile/src/packingNames.ts`(띄어쓰기·대소문자·문장부호·수량과 단위를
  뺀 이름이 같으면 같은 것). 담당은 보지 않고, 막지 않고 "이미 있어요. 그래도 추가할까요?"로 묻는다
- **아직 없는 것:** 일괄 API와 서버의 `duplicateCandidate` 경고
- 확인: 로컬 웹 빌드로 옛 준비물 3개·요리 1개(재료 2) 옮기기, 다시 기다려도 버전이 오르지 않음, 다른 기기의 체크·재료 준비
  해제·요리 추가가 다시 열면 보임, 새 기기에서 서버 목록 받기, 화면에서 체크·여러 개 추가가 서버에 저장

3번 중 비용을 하며 남긴 것:

- **지출·주고받은 기록·비용 설정이 서버에 간다.** 코덱은 `mobile/src/expenseSync.ts`. 비용 설정(통화·환율·예산·정산 묶기)은
  여행 단위라 목록 동기화가 아니라 `PATCH /trips/{id}/expense-settings`로 보내고, 버전이 어긋나면 최신 버전으로 한 번 더 보낸다

- **공간 사람 표에 없는 이름이 섞인 지출·기록은 올리지 않는다.** 이름 하나를 빼고 올리면 몫이 달라진다. 서버에서 받은

- 확인: 로컬 웹 빌드로 옛 지출·기록·JPY 설정 옮기기, 다른 기기가 바꾼 예산과 더한 지출이 다시 열면 보임

3번 중 교통편·예약을 하며 남긴 것:

확인 메일과 재설정 메일의 링크가 가리키는 페이지가 없어서, 가입은 되지만 이메일 확인과 비밀번호
재설정이 불가능했다. API 서버가 `/auth/verify-email`·`/auth/reset-password`·`/auth/forgot-password`
HTML 페이지를 직접 보여 주게 했다. GET은 아무것도 바꾸지 않고 버튼(POST)으로만 확인·변경한다.
앱 로그인 화면에 `비밀번호를 잊었어요`를 넣었다. 배포 스크립트가 nginx 설정 변경을 반영하지 않던
문제도 함께 고쳤다(내용이 바뀌면 nginx 컨테이너를 다시 만든다).

### 웹 재확인과 바뀐 이메일 (2026-09-16)

비밀번호 없이 소셜 로그인으로만 가입한 계정은 계정 삭제·비밀번호 정하기·이메일 바꾸기 앞에서
제공자로 다시 로그인해 확인받는다(`POST /v1/auth/oauth/reauth`). 이 길은 로그인과 같은
`openSocialLogin` 을 쓰므로 웹에서도 팝업으로 열리고 같은 출처의 `/oauth` 로 돌아온다.
팝업이 막히면(누른 직후가 아니거나 브라우저가 거절) `확인 창이 차단됐어요…` 를 화면에 적는다.
사용자가 창을 먼저 닫으면 취소로 보고 아무 문구도 띄우지 않는다.

이메일은 새 주소로 간 링크를 눌러야 바뀌어서, 열려 있는 앱은 그 사실을 모른다. 앱이 다시
앞으로 올 때(웹은 탭으로 돌아올 때)와 계정 화면을 열 때 `GET /v1/me` 를 다시 받아 화면과
저장된 세션을 맞춘다. 이메일 바꾸기를 요청한 직후 10분만 20초마다 한 번 더 본다. 바뀌면 멈춘다.
이름은 서버 값으로 덮지 않는다. 계정 화면에서 고치는 중이면 치던 글자가 되돌아가기 때문이다.
서버는 그대로 두고 앱만 고쳤다.

### 웹 버전 (2026-09-16)

앱 코드를 그대로 웹으로 내보내 `www.daymo.xyz/app`에 올린다. iPhone 앱이 나오기 전에
휴대폰 브라우저로 쓰는 곳이다. 자세한 것은 `site/README.md`.

- **사이트와 앱을 한 번에 만든다.** `node site/build.mjs`가 소개·약관·처리방침 페이지를 `site/dist`에
  만들면서 `npx expo export -p web`을 `dist/app`에 함께 돌린다. 앱 쪽 주소 앞부분은 `mobile/app.config.js`가
  `DAYMO_WEB_BASE_URL=/app`을 읽어 `experiments.baseUrl`로 넣는다. 사이트 글만 볼 때는 `--no-app`
- **배포는 Vercel 프로젝트 `daymo-site`에 `site/dist`를 올리는 것이다.** 저장소 push로는 배포되지 않는다.
  예전에 웹 앱을 올리던 `daymo` 프로젝트는 2026-09-15에 도메인만 떼어 두었다
- **API의 `CORS_ORIGINS`에 이 주소가 있어야 브라우저가 API를 부를 수 있다**(기본
  `https://www.daymo.xyz,https://daymo.xyz`). 토큰을 쿠키가 아니라 `Authorization`으로 보내므로
  credentials는 켜지 않는다
- **소셜 로그인은 팝업이다.** 웹은 `daymo://oauth` 대신 같은 출처의 `/oauth`로 복귀한다. `site/build.mjs`가
  만드는 `vercel.json`이 `/oauth`를 앱 번들로 리라이트하고, 번들은 그 주소에서
  `WebBrowser.maybeCompleteAuthSession()`을 불러 원래 창에 결과를 넘기고 팝업을 닫는다. state·PKCE와
  일회용 code 교환은 앱과 똑같고 서버 코드도 같다. 서버 `OAUTH_APP_REDIRECT_URIS`에
  `https://www.daymo.xyz/oauth`·`https://daymo.xyz/oauth`(로컬은 `http://localhost:8081/oauth`)를 넣는다
- 팝업은 사용자가 누른 그 순간에 열어야 Safari가 막지 않는다. 막히면 앱이 팝업 허용 안내를 보여 준다
- 세션은 웹에서 SecureStore가 없어 AsyncStorage(localStorage)에 둔다

### 출시 뒤 유료로 열 기능: 공지 붙여넣기 (2026-09-16)

카카오톡 공지에 쌓인 여행 기록을 통째로 붙여넣어 **이미 만들어 둔 지난 여행**을 채운다.
여행을 새로 만들지 않는다. 어느 여행에 넣을지 고르고, 읽어 낸 것을 항목별로 보여 주고,
켜고 끄고 이름을 고친 뒤 넣는다. `docs/02-raw-travel-data.md` 의 서식이 기준이다.

**꺼져 있다.** `mobile/src/features.ts` 의 `NOTICE_IMPORT_ENABLED` 가 `false` 라 「여행」 탭에
버튼이 나타나지 않고, 앱 어디에도 들어가는 길이 없다. 스토어 출시 뒤 유료로 열 때 이 값 하나를
`true` 로 바꾸면 된다. 서버 설정도 결제 코드도 없다.

| | |
| --- | --- |
| 읽는 곳 | `mobile/src/noticeImport.ts` (순수 모듈, 시험 30개) |
| 넣는 곳 | `mobile/src/noticeImportPlan.ts` (순수 모듈, 시험 20개) |
| 화면 | `mobile/src/NoticeImportSheet.tsx` — 붙여넣기 → 고치기 → 결과 세 걸음 |

**읽는 것:** `# 제목: 9월 22일 ~ 9월 24일 전주 한옥마을` 머리글(기간·이름·지역, 연도가 없으면
올해로 읽되 석 달 넘게 앞이면 작년), 댓글 사이의 `,` 한 줄, `——————` 로 감싼 구획 제목
(먹고 싶은 것·해먹을 거·숙소·예약·챙길 것·교통편·기록), `[대괄호]` 상태·분류·담당,
`[주소](주소)` 로 두 번 적힌 링크(공백은 `%20` 으로), 단위 없는 수량(`소고기 250`,
`배추1/2 250(20-24장)`, `후추 솔솔`), `[재료]`·`[조리 순서]` 와 번호 목록, 이모지 섞인 제목,
`[금요일]` 아래의 `- 13:30 점심 : 소나기식당`, `- 하늘 : KTX 대전 08:10 → 전주 09:36 (예매 완료)`.

**못 읽는 것:** 요일만 적힌 일정은 여행 기간에 그 요일이 없으면 날짜를 비운다(지어내지 않는다.
화면에서 날짜 칩으로 고른다). 재료의 현지 구매/집에서는 분류에 그런 말이 있을 때만 알아본다.
서버 숙소에는 링크 칸이 없어 예약 링크는 메모로 간다. 나머지 못 읽은 줄은 버리지 않고
"읽지 못한 줄" 로 모아 보여 주고, 원하면 여행 메모로 남긴다.

**겹침과 실패:** 넣기 전에 그 여행의 장소·일정·교통편·요리·준비물·메모 이름을 받아 같은 것은
미리 꺼 두고 "이미 있어요" 를 붙인다(다른 것이면 다시 켤 수 있다). 넣다가 하나가 실패해도
멈추지 않고 끝까지 간 뒤 무엇을 넣었고 몇 개를 건너뛰었고 무엇이 실패했는지 한 줄로 알려 준다.

**남은 일:** 재료의 담당(누가 가져오는지)은 아직 전부 미정으로 넣는다. 준비물 담당은 공간 사람
표에 있는 이름만 붙고 없는 이름은 태그로 간다. 화면에서 고칠 수 있는 것은 켜고 끄기, 이름,
일정 날짜뿐이라 수량·분류는 넣은 뒤 각 탭에서 고친다. 결제와 권한 확인은 만들지 않았다.

확인: 로컬 API + 웹 빌드로 `docs/02-raw-travel-data.md` 의 전주 공지를 붙여넣어 빈 여행에
장소 5곳(숙소 포함)·숙소 1곳(체크인 15:00·체크아웃 12:00)·일정 3개·요리 6개(재료 34개)·메모 2개가
들어갔고, 같은 공지를 한 번 더 붙여넣었을 때 14개를 건너뛰었다. 꺼 둔 채로 다시 빌드해 네 탭
어디에도 버튼이 없는 것을 확인했다.

## 제품 원칙

- 앱을 열고 다음 여행을 확인하는 데 네트워크 때문에 오래 기다리지 않게 한다.
- 여행을 중심으로 일정, 장소, 준비, 요리, 기록을 구조화한다.
- 연인과 친구 공간은 같은 여행 기능을 쓰고 관계별 표현만 달리한다.
- 공동 편집에서 누가 담당하고 무엇이 완료됐는지 즉시 알 수 있어야 한다.
- 네이버·카카오 지도 링크는 지원하되 특정 제공자 링크를 필수 입력으로 만들지 않는다.
- 서버 연동 중에도 현재 UI의 빠른 반응을 유지하도록 낙관적 업데이트와 로컬 캐시를 사용한다.

## 우선순위 표기

- `P0`: 앱 출시와 데이터 안전에 필수
- `P1`: 현재 UI를 실제 기능으로 완성하는 범위
- `P2`: 출시 후 확장
- `결정 필요`: 구현 전에 사용자 승인을 받아야 하는 제품 또는 인프라 선택

## 현재 착수 판정

- 문서 설계·개발 0단계: 끝났다([`10-implementation-readiness.md`](./10-implementation-readiness.md) 9장)
- 앱 기능 구현: P0·P1 범위가 서버에 붙었다. 남은 것은 로컬 우선 동기화(outbox)와 출시 준비
- 운영 배포: 운영 API(`api.daymo.xyz`)와 소개 사이트(`www.daymo.xyz`)가 돌고 있다. 스토어 제출은
  [`release/README.md`](../../release/README.md)의 "출시를 막는 것"을 모두 지운 뒤 사용자 승인으로만 한다
