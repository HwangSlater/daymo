# 다음 앱에도 적용할 공통 규칙

## 1. 제품 정의

- 핵심 사용자와 앱을 여는 이유를 한 문장으로 정의한다.
- 가장 중요한 행동을 1~3개로 제한하고 첫 화면에 우선 배치한다.
- 감성 콘셉트와 실제 사용 목적을 별도로 정의한다.
- 화면보다 정보 구조, 데이터 관계와 권한 모델을 먼저 설계한다.

## 2. 현실적인 상태로 설계

- 최소 더미 데이터가 아니라 실제 최대 사용량에 가까운 데이터로 검수한다.
- 빈 상태, 일부 데이터, 많은 데이터, 긴 문구와 여러 멤버 상태를 모두 만든다.
- 작은 화면, 라이트·다크 모드와 시스템 큰 글자를 함께 확인한다.
- 태그나 목록이 늘어날 때 접기, 검색, 필터, 가상화 중 적절한 수단을 사용한다.

## 3. 사용자 행동 중심 UX

- 사용자가 다음에 할 일을 화면에서 바로 알 수 있게 한다.
- 버튼 이름은 실행 결과를 설명하고 같은 행동은 같은 이름을 사용한다.
- 입력 완료 뒤 사용자가 기대한 위치로 이동한다.
- 위험하거나 되돌리기 어려운 동작은 영향 범위와 확인 절차를 제공한다.
- 의미 없는 장식이나 작동하지 않는 예시 기능을 제품 기능처럼 보이게 하지 않는다.

## 4. 디자인 시스템

- 배경, 표면, 본문, 보조문구, 테두리, 강조, 성공과 위험 색을 역할로 정의한다.
- 제목, 본문, 보조문구와 버튼의 글자 크기 및 줄 높이를 토큰화한다.
- 간격, 모서리 반경, 그림자와 터치 상태를 통일한다.
- 입력, 모달, 태그, 필터, 빈 상태와 확인 창을 공통 컴포넌트로 만든다.
- 장식은 디자인 시스템 위에서 사용하며 정보 구조를 대신하지 않는다.

## 5. 모바일과 접근성

- 한 손 조작, 엄지 도달 범위, 키보드와 플랫폼 뒤로 가기를 고려한다.
- 모든 버튼, 탭, 스위치와 입력에 접근성 역할·이름·상태를 지정한다.
- 색상만으로 상태를 구분하지 않는다.
- 작은 버튼도 충분한 터치 영역을 갖게 한다.
- 큰 글자, 화면 읽기 순서, 오류 안내와 상태 변경 알림을 초기 설계에 포함한다.
- 웹 데모와 실제 모바일 기기의 입력 차이를 각각 검수한다.

## 6. 성능과 데이터 경계

- 첫 화면 렌더링과 재진입 속도를 기능 요구사항으로 관리한다.
- 개인 설정·초안·최근 기록·캐시는 로컬에, 공유 상태·권한·결제는 서버에 둔다.
- 로컬 데이터로 먼저 표시하고 서버 동기화는 백그라운드에서 수행한다.
- 오프라인 작업, 재연결과 충돌 해결 규칙을 미리 정의한다.
- 이미지, 지도와 대형 목록은 압축, 지연 로딩과 가상화를 적용한다.
- 빠른 네트워크만 기준으로 개발하지 않고 앱 크기, 메모리와 데이터 사용량을 측정한다.

## 7. 개인정보와 보안

- 기능에 필요한 정보만 수집하고 권한은 실제 사용 시점에 요청한다.
- 동의 문서 버전과 사용자의 동의 기록을 보관한다.
- 탈퇴와 데이터 삭제를 앱 안에서 제공한다.
- 더미 데이터, 로그와 공개 저장소에 실명·토큰·주소 등 민감정보를 남기지 않는다.
- 인증·인가와 입력 검증은 클라이언트가 아닌 서버에서도 강제한다.

## 8. 변경과 검증

- 하나의 커밋은 하나의 목적을 가지며 큰 실험은 별도 커밋이나 브랜치에서 진행한다.
- 기능 변경과 리팩터링을 분리한다.
- 커밋 전에 타입, 정적 검사, 핵심 사용자 흐름과 실제 기기를 검증한다.
- 문서, 화면, API와 데이터 모델이 서로 어긋나지 않게 함께 갱신한다.
- 결정 이유, 제외한 대안, 완료된 단계와 남은 위험을 기록한다.

## 9. 출시 완료 기준

- 인증과 세션 복구
- 로딩·빈 상태·오류·오프라인 처리
- 동기화와 충돌 처리
- 권한, 약관, 개인정보와 탈퇴
- 알림과 딥링크
- 앱 아이콘, 스플래시와 스토어 자료
- 접근성, 성능, 앱 용량과 실제 기기 검수
- 오류 수집, 서버 모니터링, 백업과 복구
- 테스트와 반복 가능한 배포 절차

핵심 원칙은 다음과 같다.

> 사용자가 첫 화면에서 바로 이해하고, 최소한의 동작으로 목적을 이루며,
> 데이터가 많아져도 빠르고 안전하게 사용할 수 있는 앱을 만든다.
